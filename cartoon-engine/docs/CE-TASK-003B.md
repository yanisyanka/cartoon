## Эксперимент на устойчивость seed

### Первая попытка — недействительна

Повтор запуска, собранный из записи происхождения побайтово точно, вернул
идентичный sha256 за 3.1 с вместо 24.2 с. Проверка истории показала причину:

```
первый запуск  outputs → turnaround_01-mossy_three-quarter-left_00001_.png
повтор         outputs → turnaround_01-mossy_three-quarter-left_00001_.png
```

Счётчик `SaveImage` не увеличился — граф не исполнялся. **ComfyUI кэширует
исполнение**, и повтор побайтово того же графа возвращает прежний файл, ничего не
считая. Совпадение отпечатков доказывало работу кэша, а не устойчивость seed.

Тонкость измерения оказалась в том, что эксперимент был поставлен слишком точно:
идеальное воспроизведение входа гарантирует попадание в кэш.

### Вторая попытка — со сброшенным кэшем

После перезапуска ComfyUI тот же запуск исполнился по-настоящему — счётчик
`SaveImage` дал `_00002_`.

```
запуск 1   turnaround_..._00001_.png   2af4d258d567f89082ad8c87ae23b23231867955e3ec5dcd7aa90367e1822a9e   1 215 154 байт
запуск 2   turnaround_..._00002_.png   5dbdca7d596c02b3d9b9ea6c1c776e20b860514e5ca39066a01637714cc2d69d   1 216 058 байт
```

Кадр у обоих одинаковый — 880×1184. Байты различаются, размеры файлов
различаются на 904 байта: расхождение не в контейнере PNG, а в самих пикселях.

### Вывод

**Одинаковый seed при одинаковых референсе, промпте, графе, параметрах и
окружении НЕ даёт одинаковые байты.**

```
determinism.seedStable = false
```

Записано в реестр для всех трёх моделей Qwen, участвовавших в запуске. `null`
(«не проверено») больше неприменим: факт установлен измерением.

### Причина недетерминизма

Побитовой воспроизводимости мешает не seed, а способ вычисления. Seed задаёт
начальный шум и в этом смысле работает; расходятся последующие операции:

- **неассоциативность операций с плавающей точкой на GPU.** Порядок сложения в
  параллельной редукции зависит от того, как планировщик разложил работу по
  блокам, а `(a+b)+c ≠ a+(b+c)` для float. От запуска к запуску раскладка
  меняется;
- **выбор алгоритмов cuDNN/attention на лету.** Реализация свёртки и внимания
  подбирается под доступную память и форму тензора; при 2.6 ГБ свободной VRAM из
  17 модель fp8 на 20 ГБ активно выгружается и подгружается, и путь вычисления
  зависит от текущей занятости;
- **атомарные операции без фиксированного порядка** в части ядер.

Ни одна из этих причин не устраняется настройками нашего слоя. Для побитовой
повторяемости потребовались бы детерминированные ядра, фиксированный порядок
редукции и отсутствие выгрузки весов — то есть другой режим работы ComfyUI и,
вероятно, другая видеокарта под 20-гигабайтную модель.

### Что это меняет в модели данных

```
reproducibility = stochastic
```

И остаётся такой. Класс не понижен и не повышен: `computeReproducibility`
требует для `deterministic` одновременно локального провайдера, устойчивого
seed, записанных отпечатков окружения и графа и отсутствия ручных шагов.
Устойчивость seed оказалась ложной — путь к `deterministic` закрыт по факту, а
не по осторожности.

Практическое следствие: **воспроизводима не картинка, а запуск**. По записи
можно повторить работу с теми же входами и получить изображение того же
персонажа в том же ракурсе, но не тот же файл. Для конвейера этого достаточно —
принятый ракурс хранится как байты, а не пересоздаётся; но подменить хранение
пересчётом нельзя.

### Экспериментальный файл

```
C:/AI/ComfyUI/output/turnaround_01-mossy_three-quarter-left_00002_.png
```

**Сохраняется.** Это вещественное доказательство измерения. Ассетом он не
является и в реестр не заводился: повтор ради замера — не продукция. Удаление
отложено до отдельного решения.

Первый ассет `_00001_` этим экспериментом не изменён — sha256 прежний.

## Разрешение

### Как получается 880×1184

Узел 8, `FluxKontextImageScale` — `comfy_extras/nodes_flux.py:126–148`:

```python
aspect_ratio = width / height
_, width, height = min((abs(aspect_ratio - w/h), w, h) for w, h in PREFERRED_KONTEXT_RESOLUTIONS)
```

Узел выбирает из фиксированного списка семнадцати пар ту, чьё соотношение сторон
ближе к входному. **Размер входа не учитывается вообще** — только пропорция:
17 мегапикселей эталона роли не играют.

```
эталон     3584×4800  →  0.74667
выбрано     880×1184  →  0.74324   разница 0.0034
ближайшие   832×1248  →  0.66667   разница 0.0800
            944×1104  →  0.85507   разница 0.1084
```

Все варианты списка — около 1.05 Мп. Потолок узла ≈1 Мп при любом входе.

### Принятое решение

**880×1184 принимается как контракт генерации.**

- `04_multiview_qwen.json` не меняется;
- исходники ComfyUI не меняются;
- `FluxKontextImageScale` не меняется;
- генерация остаётся в текущей сетке ~1 Мп.

Обоснование: замена узла на больший размер означала бы выход за режим, в котором
модель обучена (дрейф композиции, дублирование деталей), при почти гарантированном
OOM — при 1 Мп свободно 2.6 ГБ из 17.

**Апскейл делается позже отдельным этапом**: своя capability, свой провайдер,
свой Asset с входом `role = source` и своей записью происхождения. Это
единственный вариант, который не может изменить силуэт и композицию — выход
сэмплера к тому моменту уже зафиксирован. Апскейлеров в установке сейчас нет,
`models/upscale_models/` пуст.

## Что осталось открытым

- **Направление ¾.** Технически установлено: результат показывает правую сторону
  персонажа, что согласуется с фразой «повернуть камеру влево». Соответствует ли
  это названию `three-quarter-left` — зависит от принятой конвенции
  (камероцентричной или объектоцентричной), и решение за человеком. Ассет не
  переименовывался.
- **Пометка у первого ассета.** В его происхождении осталась причина класса
  «устойчивость seed не проверена» — она была верна на момент записи. Прошлое не
  переписывается; актуальное состояние знания живёт в реестре моделей и здесь.
- **Остальные два ракурса** (¾ справа, затылок) не запускались.
